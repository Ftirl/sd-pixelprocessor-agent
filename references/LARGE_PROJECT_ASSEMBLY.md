# 大型着色器项目：分层实现与画面组装

行为修订日期：[historical validation]。适用于复杂、多 pass、长循环或函数规模已阻碍可见交付的项目；简单函数仍按 SOP-5B 默认流程。本文明确修订 SOP-5B/DI1 的组装优先级，不改变 While、作用域、结构模式和运行时安全要求。

## 1. 先确定可见里程碑，再设计接口

从目标画面的组成和 SD 可承载的数据反推架构，再按依赖自底向上实现。这里的逆向设计不是凭截图替代源码：保留每个源 pass、函数、状态和效果与实现的映射，标注 PORTED / PARTIAL / DEFERRED / BLOCKED。

规划两条进度：可见图层交付与核心语义可行性。按背景、几何/光线、物质着色、后处理等项目实际组成逐层推进，不预设固定层名。每层先交付可计算、可导出、可调参的最小画面，记录该层剩余能力；不要用函数数量占比代替画面完成度。用户指定停在某层时，交付并暂停，不擅自推进后层。

先用源函数的一小段验证最难接口，再批量建图。每个增量包括目标、源码范围、接口、布局计划、原生结果、证据和下一步。不要长期只封装函数而没有可见阶段结果。

## 2. 大型函数的三层处理

1. 纯表达式：按复用性、源码职责、节点预算提取 Function Graph。明确输入输出和类型；拆分前后以相同输入进行原生对比。不要只为压低节点数制造大量微小函数。
2. 状态与控制：保留 Set/Sequence、实际 While 和更新顺序。循环体可函数化，但所有状态显式传入传出。形参与循环状态名称分离；不能以静态 PP 链冒充动态循环。
3. 图像/数据阶段：跨像素、复用预计算、多组状态或超大计算可分成多个 Pixel Processor，用纹理/LUT 交换数据。普通函数仍适合局部纯计算，不强迫所有内容放进单个 PP。

struct/inout 多返回可按字段组编码，或用 bool/枚举输出选择器多次调用。每组输出必须来自同一份不可变调用前状态；收齐全部结果后再提交更新。重复选择器并不保证只计算一次，要记录重复成本和节点规模。

Get/Set 按真实变量类型设计：标量用 float1、二维量用 float2；仅传输边界需要时打包 float4。读取已存为 float4 的状态不能直接改成 Get float1，必须同步修改声明/Set/所有消费者，或保留合法分量提取。不同分支/语句仍遵守 fresh Get 和作用域规则，不能为省节点破坏执行语义。

## 3. 多 PP 数据接口与组装

为每条边登记：生产者、消费者、字段与通道、维度、精度、范围、编码/解码、有效位、纹理尺寸、像素中心、过滤/wrap/mip/vflip、版本，以及属于当前帧还是上一帧。先用非对称、负数、大值、边界值验证传输，再接真实函数。RGBA32F 不能无条件当成 uint32 的无损载体；大整数分片须单独验证。

按依赖表组装；统一光线、相机原点、观察者、时间、分辨率和 jitter，避免各层使用不同快照。用户要全局输入时，将鼠标、位置、时间等映射到父图参数，并验证改变参数能影响相应层、恢复参数能恢复结果。端口按实例真实 ID/类型回读，不凭显示标签猜测输入输出方向。

静态多 PP 图不等于跨帧反馈。反馈须显式调度或受支持的宿主状态机制：记录 B/D/A 等 pass 顺序、初始化/重置条件、上一帧快照、当前帧提交点、帧号和时间；读写缓冲不能混淆。未实现的反馈、折射或其他源码效果属于功能缺口，不能当成数值容差。

## 4. 验证优先级：严格路径与临时画面路径

默认路径仍是 SOP-5B：独立函数数值门通过后创建正式调用方，使用原有 verified gate 工具。容易完成、影响主要效果或揭示结构错误的验证应先完成。

当剩余数值项难验证、耗时明显，而已测画面差异较小或暂无可见差异时，先给用户看代表画面与差分、误差范围、未测条件和可能影响，再问一次：

“目前剩余的是【具体残差/验证缺口】，在【已测场景】中【观察到的画面影响】，尚未证明【未测范围】。是否先完成最终画面组装，把这些精度项记录为待办，还是继续严格逐项验证？”

不能在无画面证据时断言“不影响渲染”。已有明确优先画面的答复可沿用，不反复询问；新的功能取舍超出授权才再确认。等待答复时继续不依赖该决定的工作。

用户选择后可进入 PROVISIONAL_VISUAL_ASSEMBLY：记录决定、具体函数/残差、证据、风险范围和后续复验触发条件。允许这些函数进入明确标记的临时调用方，以获取整幅画面证据；这是一条显式的非正式验收路径，不把数值 FAIL/PENDING 填进 verified 集合，不伪造 check_function_numeric_gate、require_verified_dependencies 或 check_build_stage_order 的成功。其他未列入范围的函数继续严格门槛。

临时路径仍须完成类型/端口/作用域/输出可达性、原生 cook、数据传输、有限值和合理动态范围检查；保留源码效果与状态语义。死循环风险、错误状态顺序、丢失通道、未实现功能及未定义行为不能靠视觉近似放行。真正的算法简化需要用户另行选择。

报告分别标识：结构通过、原生渲染通过、已测画面验收、源码数值等价、时序/全参数覆盖。用户可接受画面并后置残差，但不得称为全源码等价。改变相机/时间/分辨率、残差进入可见区或相关函数变动时重开对应验证。

## 5. 验证与排障收敛

保留原源码 oracle；关闭 jitter、注入匹配噪声等仅作为诊断对照，明确改动点，不能替代完整源码门。全图验收覆盖二维坐标；线性固定 stride 可能只采固定列，必须检查实际 x/y 覆盖。最终采用全分辨率比较或明确报告采样覆盖，不能称稀疏采样为全图验收。

采用非零、非对称、多时间、分支/边界与单层隔离案例；检查 finite、非全黑、动态范围和参数变化/恢复。API 成功、尺寸正确、文件存在都不等于渲染正确。难以定位时先用常量输出/哨兵输入证明执行路径，再分离传输、算法、随机数和精度问题；不要重复修改公式而无新证据。

MCP 空结果/超时是未知状态：读回图、日志、阶段标记和输出后再决定重试。重新加载恢复黑图，只能记录恢复事实，不能据此断言 GPU/TDR 或硬分辨率上限。SDK/浮点/整数结论绑定版本、输入域和实测证据，不泛化为永远不可实现。

## 6. 精简为单一 SBS 的验收

以最终输出根和实际使用入口计算依赖闭包，覆盖函数实例、嵌套动态图、父资源、位图路径及外部文件，不只检查直接资源引用。通过 SD 原生 API 迁入/重定向依赖并保存；未使用诊断图可在备份后移出交付包。不要改写计算图来凑“单文件”，除非替代实现已独立验证。

精简前后比较关键中间输出与最终画面，记录图/资源/节点数量和体积。复制到独立目录并重新加载、计算、导出，检查隐含外部依赖及输出差异。保持全局参数与正式入口可用，报告剩余宿主调度需求；单 SBS 不自动意味着具有跨帧调度。

每步记录 skill/参考章节调用、源码与包哈希、目标图、操作、回读、验证范围、结果和下一步。卡点记录首次失败、最小复现、已排除原因、当前假设和用户决定。新证据修正旧结论，不保留互相冲突的规则作为并列要求。

本指南来自黑洞移植记录：多 PP 最小验证、手动布局、V2 数值/反馈验收、V3 分层组装和单包闭包验证。项目特定效果完成度不成为通用保证；[historical validation] 的操作工具与验收检查器见 `OPERATIONAL_RECOVERY.md`；这些检查器不等于新增自动布局算法或宿主调度能力。
